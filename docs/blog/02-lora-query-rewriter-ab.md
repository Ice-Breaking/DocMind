# 用 LoRA 微调一个查询改写器：126 样本 A/B 的完整复盘

> RAG 圈有个经典的纠结："RAG 还是微调？"我的答案是：**都不是二选一——把微调用在窄任务上，做 RAG 的配件。** 这篇复盘讲我怎么用 LoRA 微调了一个 1.5B 的小模型专职做检索查询改写，126 个样本 A/B 实测 Recall@4 提升 3.97 个百分点，改写环节的 API 成本降到零。困难集零提升的归因分析可能是全文最有价值的部分——知道数字为什么停在那里，比数字本身重要。

## 一、动机：口语化提问是向量检索的盲区

我的 RAG 平台评测集里有一道题："知识库检索不准怎么办？"——期望命中的是讲检索调优的概念文档。这类口语化、换说法的提问，和文档里的规范措辞（"检索质量优化"）在 embedding 空间里距离不近，纯靠向量召回经常漏。

常规解法是让大模型在检索前先改写问题："帮我问下啥是LoRA呀？" → "什么是 LoRA？"。但每条 query 多一次云端 LLM 调用，**每次问答都为此多付几百毫秒延迟和 API 费**，为一个改写动作不值。

我的选择：微调一个 1.5B 的小模型，专职做这一件事，跑在本地 Ollama 上——改写环节边际成本为零，延迟亚秒级，而且窄任务微调后风格极其稳定。

## 二、为什么选查询改写器作为微调对象

选微调目标时我列了三个硬条件，查询改写器全中：

1. **数据天然可得**。评测集里现成有 47 条规范问题，加噪就是配对训练数据——不需要人工标注。
2. **效果可直接度量**。改写好坏不用人评，改写前后各跑一遍检索，Recall@k 就是分数。
3. **任务足够窄**。输入输出都是一句话，1.5B 完全够用。对话模型微调则数据构造贵、评测主观、还把幻觉风险直接引进主链路。

另外架构上它是**旁路组件**：改写器挂了/输出异常，退化为原查询直检，主链路无感。微调对话模型没有这种退路。

## 三、数据构造：确定性加噪，任何人重跑得到完全相同的数据集

训练数据 = 47 条种子问题 × 3 个变体，共 141 条（去除无效后 126 参与评测口径）。变体由**固定随机种子的规则加噪**生成，覆盖四类分布偏移：

- 口语化（"这是啥玩意儿"）
- 中英混杂（"RAG 的 rerank 怎么配"）
- 错字/缺字
- 前缀寒暄（"帮我问下"、"你知道么"）

之所以强调确定性：如果数据是 LLM 随机生成的，今天跑和明天跑数据集不一样，A/B 数字就不可信。**评测纪律的第一条是可复现**——种子固定、规则固定，谁在任何机器上重跑都得到同一个数据集。测试集严格留出，训练集不含其种子。

## 四、训练与部署

训练配置（LLaMA-Factory）：

| 项 | 值 |
|---|---|
| 底座 | Qwen2.5-1.5B-Instruct（ModelScope 下载） |
| LoRA | rank=8, alpha=16, dropout=0.05 |
| 超参 | lr 1e-4, cosine, 3 epochs |
| 硬件 | MacBook M4 24GB（MPS），约 10-20 分钟 |
| 数据 | ~140 条指令对，sharegpt 格式 |

过拟合防护就是三板斧：低秩 + dropout + 少 epoch，外加留出测试集监控。任务窄到"把口语问句改写成规范问句"，不需要更大的容量。

部署环节有两个实测踩坑，写给后来人：

1. **Ollama 只认 GGUF**，直接 `FROM` 一个 safetensors 目录会报 `400 Bad Request: invalid model name`。正确路径是先用 llama.cpp 的 `convert_hf_to_gguf.py` 把合并后的权重转成 GGUF，再写 Modelfile 导入。
2. **Modelfile 的 FROM 不支持相对路径**，必须绝对路径，否则 create 静默失败。

这套步骤我固化成了一个脚本（合并 adapter → 转 GGUF → 生成 Modelfile → `ollama create`），一键执行。

## 五、A/B 结果

126 个样本（47 题 × 变体），top_k=4，基线是未微调的 `qwen2.5:1.5b` 做改写：

| 口径 | 基线 | 微调后 | Δ |
|---|---|---|---|
| 总体 Recall@4 | 0.754 | **0.794** | **+3.97pp** |
| 常规集（n=81） | 0.827 | 0.889 | **+6.17pp** |
| 困难集（n=45） | 0.622 | 0.622 | ±0 |

平均改写延迟：基线 270ms / 微调 402ms（本地 F16，M4）。

常规集 +6.17pp 是实打实的收益：改写质量直接决定向量路的召回。**但困难集纹丝不动——这才是这篇复盘的核心。**

## 六、困难集零提升的归因：瓶颈根本不在改写器

拿到 ±0 我做的第一件事不是调参，而是补了一个对照实验：**对困难集的原始规范问题直接检索（完全绕过改写器）**。结果 Recall 只有 0.588。

这意味着：连"人工写好的规范问法"都只能召回 58.8%，改写器再完美也不可能把 62.2% 提上去——**瓶颈在知识库本身的内容覆盖**（示例库只有 6 个文档、12 个切片，压根不含困难集考的某些主题），而不是改写质量。

更有意思的交叉点：微调改写器输出的 0.622 **高于**人工规范问法直检的 0.588。也就是说在最难的样本上，这个小模型把口语问题改写得比人类预设的"标准问法"更贴近语料措辞。

这组对照实验给我的方法论收获：**A/B 停滞时，先归因再动手。** 如果我当时直接去加数据、加大 rank、调 epoch，大概率白忙一场——天花板根本不在模型侧。正确的下一步是扩充知识库覆盖，改写收益才会被放大。

## 七、成本账

- 微调成本：一台 M4 MacBook，20 分钟电费
- 线上成本：改写环节 **零 API 调用**（对比方案是每条问答多一次云端大模型改写）
- 延迟：402ms 本地推理，且与云端无关、不受上游限流影响

对照"每条问答多一次 qwen-turbo 调用"的方案，按我平台实测 ¥4.4/千次调用的成本线，日均千次问答的团队一年省下的是实打实的真金白银，还顺带解决了"改写环节也出域"的数据合规顾虑。

## 八、什么时候你不该做这个

诚实地说，这个方案有明确的适用边界：

- **种子问题很少**（比如 <20 条）时，加噪变体的多样性不够，微调容易过拟合到几种句式
- **查询分布漂移快**的业务，改写器需要定期重训，要有评测集维护的纪律
- **不需要省这笔 API 费**的场景，直接 prompt 大模型改写更省事——微调的收益前提是"这件事高频到值得专训一个小模型"

## 九、复现

```bash
# 1. 生成数据（固定种子，确定性）
.venv/bin/python scripts/lora/gen_rewrite_data.py
# 2. 训练（约 10-20 分钟，M4 24GB）
HF_ENDPOINT=https://hf-mirror.com .venv-lora/bin/llamafactory-cli train scripts/lora/lora_qwen_rewrite.yaml
# 3. 合并 + Ollama 托管
bash scripts/lora/merge_and_serve.sh
# 4. A/B 评测（产出全部数字）
.venv/bin/python scripts/lora/eval_rewrite.py --baseline-model qwen2.5:1.5b --tuned-model qwen2.5-rewrite-lora --report data/lora/ab_report.json
```

报告里每个数字都由最后一条命令生成。看完这篇如果你只带走一句话：**微调不是 RAG 的替代品，是它的精装修——但动工前先用对照实验确认瓶颈真的在你装修的那面墙上。**

**仓库与训练/评测脚本**：https://github.com/Ice-Breaking/DocMind （`scripts/lora/` 下从数据生成到 A/B 报告全链路可复现）
