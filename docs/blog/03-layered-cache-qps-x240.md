# 我把 RAG 的 QPS 从 3 提到 800：一次按"确定性"分层的缓存设计

> 系列第三篇。前两篇讲了检索效果怎么度量（[混合检索三路线评测](https://github.com/Ice-Breaking/DocMind/blob/main/docs/blog/01-hybrid-retrieval-rrf-rerank.md)）和怎么优化（[LoRA 查询改写器 A/B](https://github.com/Ice-Breaking/DocMind/blob/main/docs/blog/02-lora-query-rewriter-ab.md)）——但效果再好，每条查询都要付两次上游 API 的钱和延迟（一次 embedding、一次 rerank）。这篇讲我怎么把热点查询的这两次往返整个消掉：**同代码 A/B，热点查询吞吐从 QPS 3.1 提到 801，P95 从 2573ms 降到 11ms，冷查询零退化**。TL;DR 不是"加缓存"三个字，而是判据：**先证明要缓存的东西是确定性函数，再谈怎么缓存**。

## 一、先定位，再动手

混合检索全链路压测（向量召回 + BM25 + RRF + Rerank）的结论：QPS 在 3 附近封顶，瓶颈不在服务端——单次请求的服务端计算是毫秒级，大头是**每条查询一次 embedding 远程调用 + 一次 rerank 远程调用**（调优实验室的分阶段耗时里，dense 与 rerank 两个 span 占了绝大部分）。

定位清楚后，优化路径按 ROI 排序是现成的：答案级语义缓存（已建）→ 查询向量缓存 → rerank 结果缓存。前人都会告诉你"加缓存"，但很少有人说清楚**什么能缓存、什么不能**。这是我这次设计里唯一值得展开的判断题。

## 二、判据：确定性

一条缓存规则是否安全，取决于被缓存的东西是不是**确定性函数**——同样的（模型，输入）是否永远得到同样的输出。

拿 DocMind 的四个缓存层套这个判据：

| 层 | 缓存内容 | 确定性 | 失效语义 |
|---|---|---|---|
| 分词缓存 | jieba 分词结果 | 完全确定（纯 CPU 函数） | 文本不变即有效 |
| 文档向量缓存 | 切片 embedding（SQLite 持久化） | 同题同向量 | 按文本哈希键，重建时免重复调 API |
| 查询热缓存 | query embedding + rerank 结果（进程内 LRU） | 同（model, 输入）同输出 | 键含模型名与候选集指纹 |
| 答案语义缓存 | 完整问答对 | **不确定**——相似度匹配 | 阈值保守 0.92，宁可不命中不可错配 |

前三层缓存的是确定性函数的结果，**改变的是"要不要再算一次"，永远不改变"算出什么"**——所以可以放心大胆地开。第四层（语义缓存）是相似度匹配，天生有错配风险（把"张三的密码策略"匹配到"李四的密码策略"），所以它的阈值必须保守，命中后的行为也要按"可能错"来设计。

这个判据还决定了缓存粒度：我**没有**在 rerank 层之上再缓存"检索结果列表"，因为检索结果虽然也确定，但它和上层调用方（top_k、ACL 过滤）耦合，缓存它的失效成本高于收益。确定性高、复用频率高、失效成本低——三者同时满足才值得做一层。

## 三、键设计：把失效逻辑埋进键里

缓存最常见的生产事故不是性能，是**脏数据**：换了 embedding 模型，旧向量还在缓存里被命中；知识库更新了，rerank 还在给旧排序。解法不是写一堆失效钩子，而是**把失效条件编进键里**：

```python
# 查询向量：键 = (模型名, 查询哈希) —— 模型切换自动换键
key = (config.EMBEDDING_MODEL, sha256(query))

# rerank 结果：键 = (模型名, 查询哈希, 候选集指纹, top_n)
docs_fp = sha256("\x1f".join(h.text for h in candidates))
key = (config.RERANK_MODEL, sha256(query), docs_fp, len(candidates), top_n)
```

知识库一更新，召回的候选集就变，`docs_fp` 随之变化——旧条目不是"被失效"，是"永远不会被命中"，等 LRU 自然淘汰即可。**零失效代码，零失效事故**。键里用 SHA-256 指纹而非原文还有个副产品：条目不驻留用户问题明文，键内存也小。

两个容易漏的工程细节：

1. **只缓存成功结果**。rerank 超时/熔断的路径不写缓存，异常语义完全不变；反过来，熔断期间命中缓存的热点问题仍能正常返回精排结果（缓存检查先于熔断器）——上游故障时你的高频用户反而无感。
2. **命中返回拷贝**。LRU 里存的对象如果直接把引用返回给调用方，调用方原地改一个字段就污染了缓存条目——这类 bug 测试还很难抓。存取两侧都过一层浅拷贝，标量字段的代价可以忽略。

## 四、同代码 A/B：数字与口径

缓存做成环境变量开关（`QUERY_EMBED_CACHE` / `RERANK_CACHE`），**同一份代码**跑两遍压测，唯一区别是开关。口径要说准：同一套 12 个固定问题按并发 1/4/8 **各跑一遍**（每遍 12 条请求）——第一遍全冷：12 道题各自首次查询，全部 miss，走完整链路；第二、三遍同题再来：全部命中缓存（24 hit）。第二遍起建模的正是企业 FAQ 场景的重复提问形态。

| 场景 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 并发 1（12 题各 1 次，纯冷） | QPS 2.46 / P50 350ms | QPS 2.84 / P50 308ms | 缓存无收益场景——**不伤冷启动** |
| 并发 4（同题第二遍，缓存热） | QPS 2.97 / P95 1390ms | **QPS 741 / P95 6ms** | 重复问题跳过全部上游往返 |
| 并发 8（同题第三遍，缓存热） | QPS 3.10 / P95 2573ms | **QPS 801 / P95 11ms** | 命中率 67%（12 miss + 24 hit） |

三层解读，缺一层数字就会骗人：

- **热查询 ×240 是场景建模，不是通用提升**。真实流量里长尾问题占多数，它们永远走全链路——所以并发 1 那一行必须放在表里：冷查询无获益也无退化，证明缓存没有伤到长尾。
- **命中率是可观测的**，不是估的：`docmind_query_embed_cache_total{result="hit|miss"}` 和 rerank 同款计数器直接进 Prometheus，生产上命中率掉了一眼能看到。
- **240 倍的物理含义**很朴素：热查询的每请求成本从"两次网络往返"变成"两次字典查找"，瓶颈从上游 API 转移到进程内 CPU——800 QPS 是单进程 LRU 查找的正常水平，不是极限。

## 五、别人常踩的三个坑

1. **缓存了相似度匹配的答案，却按精确命中管理**。语义缓存（答案级）和确定性缓存（组件级）的风险等级完全不同，前者阈值要保守、要按知识库隔离作用域，混为一谈就会出"张冠李戴的秒回"。
2. **失效靠定时任务**。定时失效永远在"太久（脏数据）"和"太频繁（白算）"之间赌博。把失效条件编进键，让变化自动换键，就没有这个赌局。
3. **压测口径不写清楚**。只写"QPS 提升 240 倍"不写"12 个固定问题重复请求"，等于给别人递刀。冷热两行一起放，数字才立得住。
