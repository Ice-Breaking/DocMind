# DocMind 面试准备手册（数据均为实测）

> 生成日期：2026-08-17。所有指标来自本项目真实评测/压测/线上 trace，可现场复现：
> `python scripts/bench_report.py`（评测）、`python scripts/load_test.py`（压测）。

## 一、30 秒项目陈述

DocMind 是一个**企业级多助手 RAG 平台**：多知识库 + 多助手 + RetrievalOps 质量闭环 + 企业治理。
核心链路：文档入库（增量索引）→ 混合检索（BM25 + 向量 + RRF + Rerank）→ 手写 ReAct Agent（工具调用 + 证据拒答）→ 流式问答；外围是评测、告警、审计、成本的平台化能力，另含 LoRA 查询改写器（训练侧）、四层缓存体系（成本/延迟侧）、标准 MCP Server（生态侧）。

**一句话差异化**：不止"能问答"，而是"质量可度量、成本可核算、故障可告警、操作可审计"。

## 二、量化成果（背下来）

### 1. 检索质量（47 样本评测集：基础 30 + 困难 17）

| 检索路线 | 基础集 Recall@4 | 基础集 MRR | 困难集 Recall@4 | 困难集 MRR |
|---|---|---|---|---|
| 纯向量 | 100.0% | 0.978 | 94.1% | 0.843 |
| 混合 RRF | 100.0% | **1.000** | **100.0%** | 0.873 |
| 混合 + Rerank | 100.0% | 1.000 | 94.1% | **0.941** |

**解读（必讲）**：
- 混合 RRF 把困难集（口语化/英文/缩写）Recall 从 94.1% 提到 **100%**——BM25 补了纯向量的专有名词短板。
- Rerank 让困难集 MRR 从 0.873 提到 **0.941**（正确答案排得更靠前），但 Recall 掉 1 条——阈值过滤把一条边缘相关的候选砍了。**这不是缺陷，是"宁缺毋滥"的阈值语义在评测上的投影**，也是证据拒答体系的同一套哲学。
- 唯一未命中样本："知识库检索不准怎么办？"（口语化换说法，期望命中概念文档）——可作为下一轮切片/改写优化的 Badcase。

### 2. 压测报告（开放检索端点，全链路：向量+BM25+RRF+Rerank）

| 并发数 | QPS | P50 | P95 | 错误率 |
|---|---|---|---|---|
| 1 | 1.99 | 501 ms | 824 ms | 0% |
| 4 | 2.24 | 1734 ms | 2063 ms | 0% |
| 8 | 2.17 | 2528 ms | 3807 ms | 0% |

**解读（必讲）**：QPS 在 ~2.2 封顶，瓶颈不在服务端而在**上游 LLM API**（每次请求 1 次 embedding + 1 次 rerank 远程调用）。优化路径按 ROI 排序：
1. **语义缓存**（已建）：高频问题命中即秒回，跳过整条链路；
2. **Embedding 缓存**（已落地 2026-08-30，见下）；
3. Rerank 结果缓存（已落地，取代"批量合并"——候选已 ≤10 且多库合并后单次调用，批量无空间）。
"我知道瓶颈在哪、下一步压哪里"比数字本身更值钱。

**分层缓存 A/B（2026-08-30 落地后复测，同代码开关切换，可复现：`QUERY_EMBED_CACHE`/`RERANK_CACHE`）**：

| 场景 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 并发 1（12 题各 1 次，纯冷查询） | QPS 2.46 / P50 350ms | QPS 2.84 / P50 308ms | 缓存无收益场景，数字同级——**不伤冷启动** |
| 并发 4（热点查询） | QPS 2.97 / P95 1390ms | **QPS 741 / P95 6ms** | 重复问题跳过全部上游往返 |
| 并发 8（热点查询） | QPS 3.1 / P95 2573ms | **QPS 801 / P95 11ms** | 命中率 67%（12 miss + 24 hit），`/metrics` 可观测 |

**必讲三点**：① 冷查询零退化（并发 1 证明），热查询吞吐 ×240——分层缓存各司其职；② 正确性设计：embedding/rerank 对同一 (model, 输入) 是确定性函数，键含模型名与候选集指纹，模型切换/知识库更新自动换键失效，无需手动清缓存；③ 与答案级语义缓存、文档侧切片向量缓存、CPU 级分词缓存构成**四层缓存体系**，按"确定性 + 失效成本"逐层设计——这是缓存架构题的标准答案素材。

### 4. LoRA 查询改写器 A/B（训练侧，2026-08-26 实测）

口语化/中英混杂提问拉低向量召回——微调 Qwen2.5-1.5B（rank8 LoRA，LLaMA-Factory，本地 Ollama 托管）
专职查询改写，替代"每次问答让云端大模型顺手改写"（该环节边际成本归零，本地亚秒级）。
126 样本 = 47 题 × 3 确定性加噪变体，top_k=4：

| 口径 | 基线 qwen2.5:1.5b | 微调 qwen2.5-rewrite-lora | Δ |
|---|---|---|---|
| 总体 Recall@4 | 0.754 | **0.794** | **+3.97pp** |
| 常规集（n=81） | 0.827 | 0.889 | **+6.17pp** |
| 困难集（n=45） | 0.622 | 0.622 | ±0 |

平均改写延迟：基线 270ms / 微调 402ms（本地 F16）。复现：`scripts/lora/README.md`（数据确定性生成 → 训练 → 合并 GGUF → `eval_rewrite.py` 出报告）。

**困难集零提升的归因（加分点，必讲）**：对 HARD_SET 规范问题直接检索（完全不经改写器）Recall 仅 0.588——瓶颈在示例知识库内容覆盖（6 文档/12 chunks，不含 MCP、端口冲突等主题），而非改写质量；且微调版改写后的 0.622 **高于人工规范问法直检的 0.588**，说明小模型改写器在最难样本上已不输人工。结论：扩知识库后改写收益才会放大——"知道数字为什么停在这里"比数字本身更加分。

## 三、设计取舍 Q&A（面试官最爱问"为什么"）

**Q1：为什么用 RRF 融合而不是分数加权归一化？**
RRF 按排名（1/(k+rank)）融合，天然免疫两路分数量纲差异（BM25 无上界，向量余弦 0~1），零调参、对异常高分鲁棒；归一化要处理分布假设和离群值，k=60 是论文验证过的经验值。代价是丢失分数绝对语义——所以我把阈值判断放在 rerank 之后，RRF 分数只用来排序。

**Q2：Rerank 阈值为什么不用固定值？**
固定阈值会随语料/模型漂移失准。我用"绝对下限 0.05 + 头部相对比例 15%"双条件：头部候选 <0.08 直接判整体无关（触发拒答链）；其余候选跟头部比而非跟固定线比。评测证据：困难集 MRR 0.873→0.941。

**Q3：证据拒答为什么确定性替换，而不是提示词约束模型？**
提示词依从性是非确定的（我们评测中确实发现 LLM 偶发漏标 OOD 标注）。企业问答的防幻觉必须是**代码级兜底**：KB 无证据且无联网结果时，Agent 直接替换最终回答为拒答文案并写 trace 事件，模型没有"发挥空间"。开关化（EVIDENCE_REFUSAL）保证可回退。

**Q4：为什么手写 ReAct 而不用 LangChain？**
三个理由：① 流式（token 级增量 + 思维链）在框架里是二等公民，手写 generator 完全可控；② 安全守卫（prompt 注入检测、OOD 标注、重复调用熔断、证据拒答）需要插在循环的精确位置，框架钩子不够细；③ 全链路 trace 埋点与自有评测体系同构。代价是工具生态要自己接——我用 MCP 协议补上了。

**Q5：降级链怎么设计的？**
每一级外部依赖都有确定性降级：Rerank 失败→RRF 结果；Langfuse 不可用→本地 JSONL；Tavily 失败→SearXNG；模型不支持思维链→自动去掉参数重试；LDAP 不可达→本地账号不受影响。原则：**追踪/增强类功能故障绝不阻断问答主链路**。

**Q6：索引为什么增量而不是每次全量？**
逐文件指纹 manifest 对比，只对变化文件重新切片+向量化。实测一次"新增 1 文件"的重建：全量需 29 个切片全部重嵌，增量只嵌 1 个——embedding 成本直降 96%。Chroma 持久化 + version 号让检索器懒重建 BM25，无需手动同步。

**Q7：API Key 为什么只存哈希？**
明文只在创建时返回一次，库里存前缀（展示）+ SHA256（校验），DB 泄露不泄露密钥；配合 scope（按知识库授权）、轮换（旧 key 立即失效）、吊销、过期四件套，对齐企业密钥治理基线。

**Q8：备份为什么用 VACUUM INTO？**
SQLite 官方热备原语，WAL 模式下不阻塞写入、产物是一致性快照；配合文档目录打包成单个 zip，恢复就是"停服-解压覆盖-重启"三步演练。

**Q9：告警为什么做 dedupe_key？**
同一问题在周期评估下会反复命中，按 dedupe_key 对 open 状态去重，避免告警风暴淹没真正的新问题；解决后条件再犯会重新开新告警，生命周期清晰。

**Q10：查询级热缓存怎么保证不出错答案？（2026-08-30 新增）**
只缓存**确定性函数**的结果：embedding 与 rerank 对同一（model, 输入）输出恒定，缓存改变的是"要不要再算一次"，不是"算什么"；而答案级语义缓存是相似度匹配有错配风险，所以阈值保守（0.92）。失效靠键设计：键含模型名与候选集 SHA-256 指纹，模型切换/知识库更新后自动换键，无需手动清缓存。只缓存成功结果——rerank 失败/熔断语义不变，熔断期间命中缓存的热点问题反而仍能正常精排（缓存先于熔断检查）。

**Q11：热点查询 ×240 是不是刷出来的数字？**
压测口径写得很清楚：12 个固定问题在并发 4/8 下重复 4/8 次——这是"企业 FAQ 热点场景"的建模，不是通用负载。冷查询（并发 1，每题只查一次）2.46→2.84 QPS 无退化，证明缓存不伤长尾；`/metrics` 的 hit/miss 计数（12 miss + 24 hit，命中率 67%）可现场复现。两个数字一起讲，比单讲 240 诚实得多。

**Q12：把知识库开放成 MCP 工具，安全边界在哪？**
MCP server 只持有 API Key 并转发 HTTPS 请求到开放端点，不落任何知识数据；文档级 ACL、每 Key 限流、审计全部继承服务端策略（与 curl 调 /open/v1/retrieve 同一权限面）；下载类外呼（TTS 音频）有域名白名单 + 公网 IP 校验 + 禁重定向的 SSRF 防护。错误文案对客户端输出自然语言（不暴露端点/凭证线索）。

**Q13：训练侧为什么选查询改写器，而不是微调对话模型？**
数据可得性（eval_set 天然提供规范问题，加噪即得配对）、效果可度量（Recall@k 直接量化）、任务窄（1.5B rank8 足够，10-20 分钟可训）；对话模型微调则数据构造贵、评测主观、幻觉风险引入主链路。改写器是旁路小模型，失败可退化为原查询直检。

## 四、STAR 故事：一次质量闭环

- **S**：困难集评测发现"知识库检索不准怎么办？"未命中——口语化换说法是纯向量盲区。
- **T**：在不增加模型成本的前提下提困难集 Recall。
- **A**：定位到 BM25 路本可命中但排名靠后 → 引入 RRF 双路融合 + 多轮查询改写（指代消解）→ 评测集回归验证。
- **R**：困难集 Recall 94.1%→100%，MRR 0.843→0.873；该流程固化成平台能力：差评→Badcase 页流转→评测集加样本→一键跑批回归。

## 五、可能被追问的问题（备好答案）

1. **多知识库检索怎么合并排序？** 各库双路召回不精排 → 合并去重保留高分 → 统一 rerank 一次（省 API 且跨库可比）。
2. **切片策略？** 280 字符 + 40 重叠，中文 QA 文档小切片防稀释；PDF/Word/Excel 纯 Python 提取，图片走 OCR 抽取。
3. **会话安全？** prompt 注入双向防护（用户输入高危拦截 + 工具结果不可信数据清洗）、文档级 ACL（无权文档过滤且与"真没有"同话术，不泄露存在性）。
4. **可观测性？** trace 五类 span（generation/retrieval:dense/sparse/rerank/evidence-refusal）带 kb 标签，检索日志页五维过滤；Prometheus /metrics。
5. **为什么可用率不是 99.9%？** 诚实回答：5.15% 失败主要是 query 改写副任务的瞬时错误与评测期模型调用抖动，主链路有重试兜底；SLA 口径已按天趋势监控，这正是告警系统的输入。
6. **成本怎么再降？** 分层缓存已落地（语义缓存 + 查询级 embedding/rerank 热缓存，热点问题上游调用归零）、大小模型路由（改写/追问用 flash 级模型，已在用；寒暄分流本地小模型）、下一步是 rerank 候选收缩与轻量 embedding 模型替换。
